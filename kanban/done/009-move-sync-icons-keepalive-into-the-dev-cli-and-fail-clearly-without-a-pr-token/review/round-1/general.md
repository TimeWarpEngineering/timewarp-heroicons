## Summary

`dev workflow-keepalive --workflow <file>` PUTs `/repos/{owner}/{repo}/actions/workflows/{file}/enable` with the lookups HTTP shape (User-Agent `timewarp-heroicons-dev-cli`, `application/vnd.github+json`, Bearer token, 60s timeout) plus `X-GitHub-Api-Version: 2022-11-28`. Repo comes from `--repo` or `GITHUB_REPOSITORY` and must be `owner/name`. Token comes from `GH_TOKEN`, then `GITHUB_TOKEN`. Any 2xx prints the status and returns success. A missing workflow, repo, or token, a non-2xx response (401/403/404 hints plus a trimmed body), a transport error, or a timeout prints one error line and sets exit code 1. Nuru documents that `Environment.ExitCode` is the process exit code. The recorded smoke covers missing repo (exit 1), a bogus token (401, exit 1), and a real token (204, exit 0).

The `keepalive` job stays a separate job with no `needs`. It checks out, sets up .NET 11, and runs `dotnet run tools/dev-cli/dev.cs -- workflow-keepalive --workflow sync-icons.yml`, then `exit $LASTEXITCODE`. There is no inline `gh api`. Workflow-level `permissions: {}` still stands, so the job token only has what the job lists: `actions: write` and `contents: read`. The task and the restatement both say `actions: write` only. That wording described the old one-line `gh api` step, which did not need the tree. The same requirement now says to run the dev-cli, and checkout cannot fetch it without `contents: read`. The job does not gain `contents: write` or `pull-requests: write`. Results, the YAML comment, and the readme name `contents: read` as the checkout permission. The design comment in `workflow-keepalive-command.cs` still says `actions: write` only; the comment's point, that a failing sync does not skip keepalive, is still true, and the YAML is the permission list. Not a finding. Token order prefers `GH_TOKEN`, which is what this job sets and what `gh` uses. `update-icons` lookups still prefer `GITHUB_TOKEN` so the release lookup stays on the workflow token when `GH_TOKEN` is the PAT. Each call site matches its workflow env. Not a defect.

`dev update-icons --pr` calls `WarnWhenSyncTokenMissing` after the repo-root check and before the upstream lookup, so an already-up-to-date run still warns. The warning prints only when `GITHUB_ACTIONS` is true and `HEROICONS_SYNC_TOKEN_SET` is not true. It is plain text, so the `::warning::` command starts the line, and it does not set an exit code. The workflow sets the flag with `secrets.HEROICONS_SYNC_TOKEN != ''` and still falls back with `HEROICONS_SYNC_TOKEN || GITHUB_TOKEN`. On `gh pr create` failure, `CommandOutput.Combined` (stdout and stderr in order) is matched for the task's permission signals: "not permitted to create or approve pull requests", "Resource not accessible by integration", `HTTP 403`, and `403 Forbidden`. A match prints both fixes: a fine-grained `HEROICONS_SYNC_TOKEN` for this repo (Contents and Pull requests read and write) and the Actions setting, including the org-policy case, then exits 1. The branch is left in place. Results record that this 403 path was not run live; the matchers line up with those GitHub messages. The recorded smoke covers the warning on and off, both with exit 0 while icons are current.

The readme section "Syncing icons and releasing" has the one-time secret setup, the two scopes, the `GITHUB_TOKEN` fallback, the no-CI warning, the permission failure, PAT renewal, and the keepalive command. `glossary.md` still defines keepalive as the job that re-enables the workflow and makes no commits. The secret name is used one way. No new term is used two ways.

The restatement matches the task, including the `actions: write` only sentence. The `contents: read` addition is an implementation deviation recorded under Results, not a misread. No check was silenced or weakened. `Directory.Build.props` `NoWarn` is unchanged. Recorded gates cover the delta: `./bin/dev build`, `dotnet run --file tools/dev-cli/dev.cs -- self-install`, actionlint v1.7.12, `./bin/dev test`, and `ganda repo audit` (the same two pre-existing advisories).
